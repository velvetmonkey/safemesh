# Node persistence adapter proposal

Status: design only. This branch changes no public API, binding, signed payload, or peer wire format. The proposed storage envelope is local data, with a versioned decoder; it needs no signed or wire change. If a later implementation changes either signed or peer wire bytes, Ben must rule on that change first.

## Evidence and ceremony on main

The long Node walk has one `writeFileSync` call site inside `save`, executed for each counter log and set identity (`rust/crates/safemesh-wasm/examples/node-persist.mjs:45-51`), one set `importIdentity` and one counter `mergeLogBytes` on load (`:62-81`). `persist` creates, edits, exchanges, shows state, then saves both sides (`:105-139`); `restore` loads both (`:141-149`); `partition` loads, edits, shows, then saves (`:151-166`); `reconcile` loads, exchanges, shows, then saves (`:168-179`). The prose duplicates that executable example, including the save and import sites (`rust/crates/safemesh-wasm/PERSIST.md:145-190`) and teaches the four process steps (`:315-322`, `:324-399`). Its per-file `wx` check protects the initial exercise from overwrite, but later `w` writes are separate, non-atomic files.

The TypeScript gold-path fixture has **eight** `writeFileSync` call sites: initial counter and identity (`examples/gold-path/typescript/main.ts:32-33`), post-restart pair (`:47-48`), two peer identity saves (`:56`, `:60`), and final local pair (`:63-64`). It imports an identity at restart (`:40`) and again to verify the final saved copy (`:97`). The docs copy repeats those eight sites and both imports (`docs/src/content/docs/using-safemesh.md:462-494`, `:527`); the short page describes the save/restart steps and their limits (`docs/src/content/docs/persist-and-restart.md:276-297`). Thus the two executable Node paths contain nine syntactic save sites, and their teaching pages repeat nine; there are two executable restart import sites in the gold path plus one in the long walk, with corresponding prose copies. These counts are source sites, not runtime write totals.

The binding currently mutates live handles in `appendBump` and `mergeLogBytes` (`rust/crates/safemesh-wasm/src/lib.rs:539-622`) and in allocated set append/import (`:1398-1450`); `exportIdentity` includes writer count, author, next allocation sequence and checked complete log (`:1408-1450`). It has no storage callback. `wasm-bindgen` already imports and calls JavaScript functions synchronously through `inline_js` externs (`:14-97`), so a synchronous JavaScript storage callback is feasible at this boundary. Callback exception propagation, reentrancy, and transaction ordering remain implementation work and require a running prototype.

The Rust comparison is `DurableReplica`: fresh construction creates a missing root, refuses an existing transaction and commits initial state (`rust/crates/safemesh-crdt/src/local.rs:412-474`); accepted edits commit before becoming visible (`:476-549`). Restart requires the existing root and fence, validates committed metadata and history under its lock (`:566-665`). `restart_counter_from_store` reads the count and writer from committed metadata under that same lock, refuses missing/truncated/invalid data, then performs checked replay (`:678-708`). These are requirements for the Node proposal, not promises made by the current Node binding.

## One adapter shape

Add **managed Node handles** for the [v0 focus](https://velvetmonkey.github.io/safemesh/#v0-support) G-Counter and allocated UTF-8 OR-Set. A factory accepts `{ mode: "fresh" | "restart", writer, writers? }` and one synchronous `Store` callback object. In `fresh`, `writers` is required; in `restart`, the adapter obtains it only from committed metadata. The public handle exposes checked edit, receive, state and peer-byte methods. It does not expose the underlying mutable WASM replica; the existing low-level API remains available separately. A handle owns one writer lease until `close` and becomes permanently write-disabled after an ambiguous or failed commit until closed. The adapter must reject callback reentry into the same handle.

`Store.open(mode, writer)` atomically claims exclusive ownership and returns a lease. In `fresh`, it creates the missing root on first use and refuses any existing store/transaction; in `restart`, it requires an existing root and committed transaction and never creates either. `Store.readCommitted(lease)` returns one complete versioned local envelope plus a revision, or a typed missing/corrupt failure. The envelope contains kind, committed writer count, writer id, allocation cursor and complete validated log/identity. On restart, the adapter validates envelope version, kind, count, author, cursor and full replay **before** returning a handle. A counter's width is derived from the committed count, never a caller-supplied restart value. It refuses invalid metadata and never treats a missing or damaged store as fresh.

For each local edit or accepted peer record, the managed handle builds a private candidate and encodes its complete next envelope. It calls `Store.commit(lease, expectedRevision, nextBytes)` synchronously. The store must atomically replace the committed envelope and advance its revision, or throw. Only after commit succeeds does the handle publish candidate state, return success or record bytes, or allow those bytes to be sent. Duplicates need no commit and collisions fail. A batch either commits one checked candidate or returns no accepted prefix. Callback failure retains the lease and disables writes; the application closes it and explicitly restarts from the last verified commit. `Store.close(lease)` releases the ownership claim. The lease spans read, replay and every commit; `commit` must reject an obsolete revision or lost lease. A storage implementation cannot claim this contract if it cannot supply exclusive ownership and atomic compare-and-replace.

The shape makes acknowledgement-before-save impossible through the managed API: no public candidate or success exists before `commit` returns. The low-level binding remains caller-managed. A stale *but self-consistent* identity is detectable only if the store compares it with a monotonic committed revision or other independent high-water mark that was not rolled back with the snapshot. `Store.open`/`readCommitted`/`commit` therefore require that anchor and reject stale revisions. If the entire store **and** its independent anchor are restored together, no local adapter can infer an unseen acknowledged edit; recovery requires an external authority or a new writer identity. The Rust path likewise cannot prove detection of a whole-store rollback. Missing restart directories are refused; missing fresh roots are created. No guarantee is relaxed to simplify Node.

The application supplies and chooses the store implementation. It decides filesystem durability, `fsync` and directory-sync policy, storage medium, backup and restore policy, retention of the independent revision anchor, and when to tell a user that the chosen policy is durable. A plain `writeFileSync` store cannot claim the Rust file-and-directory-sync acknowledgement guarantee. A Node filesystem store seeking parity must implement atomic replacement, suitable sync, exclusive cross-process ownership, and reliable error reporting; the callback interface by itself does not establish those properties.

## Public API surface and browser consequence

Implementation would add a managed-handle factory for each [v0 focus](https://velvetmonkey.github.io/safemesh/#v0-support) kind, its checked edit/receive/read/close methods, and a typed synchronous `Store` callback contract (`open`, `readCommitted`, `commit`, `close`) in generated Node declarations. It would add local envelope version/error types. Existing `appendBump`, `appendAllocatedAdd`, `exportIdentity`, `importIdentity`, and peer bytes need no signature change. No proposed addition is a signed shape or peer wire shape; the envelope is local storage and must not be sent as a peer record. A future migration from existing loose files requires an explicit one-time import procedure and validation, never an implicit fallback from failed managed restart.

The browser IndexedDB path cannot use this *synchronous* callback shape as-is: IndexedDB commits are asynchronous and browser ownership is shared across tabs. It can share the envelope validation and candidate/commit/publish state machine, but needs an asynchronous adapter with an IndexedDB transaction and a cross-tab ownership protocol. One conceptual contract serves both environments; one synchronous public API does not. No browser code or behavior changes on this branch.
